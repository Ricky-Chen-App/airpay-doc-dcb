    Dokumentasi API Airpay Direct Carrier Billing (DCB)

    Panduan integrasi untuk merchant dan partner: langganan DCB lewat HE + OTP dan OTP Flow, lengkap dengan notifikasi MO dan DN. Base URL: {domain} (lihat Pendahuluan).

    Airpay

    API Reference Airpay DCB

    Spesifikasi teknis setiap endpoint: parameter, header, response, dan contoh. Penjelasan konsep ada di tab Docs.

    Pendahuluan

    Direct Carrier Billing (DCB) HTTP API memungkinkan merchant (Service Provider) yang telah diotorisasi menagih pengguna seluler langsung melalui pulsa (prabayar) atau tagihan pascabayar saat mereka membeli konten digital atau layanan berlangganan. Pengguna menyelesaikan pembayaran cukup dengan mengonfirmasi transaksi lewat nomor ponselnya, tanpa kartu kredit atau Digital Payment.

    Sangat disarankan mengintegrasikan API sesuai dokumen Service Program yang diberikan tim teknis Airpay saat setup layanan, agar sesuai dengan persyaratan telco dan alur end-to-end berjalan lancar. Baru mulai? Lihat Alur integrasi, lalu Skenario UAT dan Checklist go-live.

    Base URL

    Contoh memakai placeholder {domain}. URL lengkap = {domain} + path. Untuk OTP Flow base URL-nya https://api.airpay.mobi. Nilai {domain}, {CHANNEL}, {TELCO}, {SERVICE}, dan {APIKEY} diberikan tim integrasi saat setup layanan.

    Konvensi umum

    • Semua request memakai HTTP(S) dengan method GET; parameter dikirim lewat path dan query string.
    • Respons berformat JSON dengan field code dan message.
    • Daftar kode error ada di Daftar Kode Error.
    • Nilai di dalam kurung kurawal { } bersifat dinamis dan harus diganti dengan nilai sebenarnya.
    • Notifikasi hasil (MO dan DN) dikirim ke URL merchant; siapkan endpoint penerimanya (lihat Persyaratan integrasi).

    Lingkungan dan keamanan

    Gunakan staging untuk pengembangan dan UAT. Pindah ke produksi hanya setelah UAT lolos dan aktivasi disetujui tim Airpay.

    LingkunganBase URLCatatan
    Staging{BASE_URL_SANDBOX}Untuk pengembangan dan UAT. Kredensial terpisah dari produksi.
    Production{BASE_URL_PRODUCTION}Hanya setelah UAT selesai dan aktivasi disetujui.
    Kredensial (apikey, client id, client secret) serta kode channel, telco, dan service diberikan tim integrasi Airpay. Nilai harus berasal dari lingkungan yang sama dengan base URL yang dipakai.

    Keamanan

    • Semua panggilan memakai HTTPS. Endpoint MO dan DN merchant juga sebaiknya HTTPS.
    • apikey dan client secret bersifat rahasia. Simpan di server, jangan di aplikasi klien, halaman web, atau repositori kode, dan jangan tampilkan di log.
    • Karena apikey berada di query string pada sebagian endpoint, pastikan log akses dan proxy tidak menyimpan URL lengkap.
    • Terima notifikasi MO, DN, dan callback portal hanya dari IP Messaging Platform Airpay: {CALLBACK_SOURCE_IP}
    • Aturan signature (bila berlaku untuk layanan Anda): {SIGNATURE_RULE}. Error 900 berarti signature tidak valid.

    Basic Auth (khusus Request Token)

    Endpoint Request Token memakai HTTP Basic Auth. Username adalah client id merchant dan password adalah client secret. Kredensial di-encode Base64 dengan format username:password dan dikirim pada header Authorization.

    FieldNilai
    username (clientId)YOUR_CLIENT_ID
    password (clientSecret)YOUR_CLIENT_SECRET
    Authorization: Basic WU9VUl9DTElFTlRfSUQ6WU9VUl9DTElFTlRfU0VDUkVU

    Bearer Token (endpoint lain)

    Token dari Request Token dikirim sebagai Bearer Token pada semua endpoint berikutnya (Send OTP, Confirm OTP, Unsubscribe) lewat header:

    Authorization: Bearer <token>
    Penting: Bearer token kedaluwarsa setiap 1 jam. Bila sudah kedaluwarsa, panggil Request Token lagi untuk mendapat token baru.

    Parameter umum

    Nilai di dalam kurung kurawal { } bersifat dinamis dan harus diganti saat memanggil.

    ParameterWajibKeterangan
    apikeyYaAPI key merchant: YOUR_API_KEY.
    serviceYaKode layanan yang dilanggani.
    clickidYaID sesi/klik pelanggan yang unik (pelacakan).
    msisdnYaNomor telepon pelanggan.
    otp_keyYaOTP key yang dikembalikan endpoint Send OTP.
    otp_valueYaKode OTP yang diterima pelanggan lewat SMS dari {your SDC}.

    Catatan penting

    • Bearer token kedaluwarsa setiap 1 jam; panggil Request Token lagi setelah kedaluwarsa.
    • username = client id merchant, password = client secret merchant.
    • Request Token memakai Basic Auth dengan encoding Base64 (format username:password).
    • Semua endpoint kecuali Request Token wajib menyertakan header Authorization: Bearer <token> dan header apikey.
    • Kode OTP dikirim lewat SMS dari sender/SDC {your SDC}; nilainya dipakai sebagai otp_value pada langkah Confirm OTP.
    • API key dan client secret bersifat rahasia; jangan dibagikan ke pihak yang tidak berwenang.

    Spesifikasi endpoint OTP Flow ada di API Reference › Request Token dan seterusnya.

    Notifikasi MO dan DN

    Hasil transaksi dikirim Airpay ke URL merchant (CP) dengan method GET. Ada dua jenis notifikasi: MO saat pengguna memulai permintaan dari ponselnya, dan DN yang menandakan apakah pesan terkirim dan ditagihkan ke ponsel pengguna.

    NotifikasiEventArti
    MOMOREGMO untuk langganan (registrasi).
    MOMOUNREGMO untuk berhenti langganan.
    DNFPNotifikasi pembelian pertama (First Purchase).
    DNRENEWALNotifikasi perpanjangan (renewal).
    • Pastikan firewall server CP mengizinkan akses dari IP Messaging Platform Airpay.
    • Balas OK dengan HTTP 200 bila proses berhasil.
    • Gagal terkirim ke handset dikembalikan sebagai negative acknowledgment (FAIL); kode status DN ada di Kode status DN.
    • msisdn dapat terenkripsi tergantung geo dan layanan.

    Spesifikasi parameter ada di API Reference › MO HTTP Interface dan Delivery Notification.

    Menangani notifikasi MO dan DN

    • Balas OK dengan HTTP 200 secepat mungkin, lalu proses di belakang. Balasan lain dianggap gagal terkirim.
    • trx_id berasal dari merchant, jadi buat unik untuk setiap transaksi dan gunakan sebagai kunci unik. Notifikasi yang sama dapat datang lebih dari sekali, jadi proses secara idempoten dan abaikan trx_id yang sudah diproses.
    • Jangan menganggap urutan MO dan DN pasti. Gunakan event dan trx_date untuk menentukan status akhir.
    • Simpan notifikasi mentah (parameter lengkap) untuk audit dan rekonsiliasi.

    Penanganan error (rekomendasi)

    KodeTindakan
    500Kesalahan di sisi Airpay. Ulangi dengan jeda bertahap (backoff) dan batasi jumlah percobaan. Bila terus gagal, hubungi dukungan.
    901, 902Token tidak valid atau kedaluwarsa. Ambil token baru lewat Request Token, lalu ulangi sekali.
    907, 9071, 9072OTP salah, atau otp_key tidak ditemukan atau kedaluwarsa. Minta pelanggan memasukkan ulang, atau kirim OTP baru.
    908, 909, 910Channel, telco, atau layanan belum aktif. Jangan diulang; hubungi tim Airpay untuk aktivasi.
    911trx_id duplikat. trx_id dibuat merchant dan harus unik per transaksi; jangan pakai ulang ID yang sama.
    400, 903 - 906, 912Request atau parameter tidak valid. Perbaiki request, jangan diulang apa adanya.

    Checklist go-live

    Centang setiap butir sebelum meminta aktivasi produksi. Bila ada yang belum terpenuhi, tunda go-live.

    Kredensial dan konfigurasi

    • apikey, client id, client secret, dan base URL produksi sudah diterima dan berasal dari lingkungan yang sama.
    • Kode channel, telco, service, dan SDC yang akan dipakai sudah dikonfirmasi aktif.
    • Satu URL MO dan satu URL DN produksi sudah diberikan ke tim Airpay.
    • URL MO dan DN dapat dijangkau dari internet, dan firewall mengizinkan IP Messaging Platform Airpay.
    • Kredensial disimpan di server (secret manager atau variabel lingkungan), bukan di kode atau aplikasi klien.

    Integrasi

    • Semua skenario di Skenario UAT lolos di staging dan buktinya sudah dikirim.
    • Endpoint MO dan DN membalas OK dengan HTTP 200 dan memproses notifikasi secara idempoten berdasarkan trx_id.
    • Status DN gagal (kode 600 dan seterusnya) ditangani sesuai Kode status DN.
    • Token OTP Flow diperbarui otomatis sebelum atau saat kedaluwarsa (1 jam).
    • Penanganan error mengikuti Praktik operasional, termasuk batas percobaan ulang.
    • Callback ke portal (subscribe, unsubscribe, renewal) sudah diterima dan memperbarui status pengguna.

    Operasional

    • Log request, response, dan notifikasi mentah disimpan tanpa memuat apikey atau client secret.
    • Pemantauan dan peringatan untuk lonjakan error, notifikasi berhenti, dan token gagal diperbarui sudah aktif.
    • Rekonsiliasi berkala dengan Report / Reporting Details di reports.airpay.mobi sudah dijadwalkan.

    Langkah aktivasi

    1. Kirim hasil UAT dan konfirmasi checklist ini ke tim Airpay.
    2. Tim Airpay memverifikasi dan mengaktifkan layanan di produksi.
    3. Lakukan satu transaksi uji nyata dengan nomor milik tim Anda: langganan, notifikasi MO dan DN, lalu berhenti langganan.
    4. Pastikan transaksi muncul di Report / Reporting Details dan datanya cocok dengan sistem Anda.
    5. Buka layanan ke pelanggan dan pantau 24 jam pertama.

    Ikhtisar OTP Flow

    Panduan integrasi langganan lengkap untuk OTP Flow, versi 2 (DCB v2), memakai endpoint /api/v2/ext/*. Setiap request, kecuali Request Token, memerlukan Bearer Token pada header Authorization. Token diperoleh lebih dulu lewat Basic Auth. Detail autentikasi ada di Autentikasi.

    FiturEndpoint
    Langkah 1: ambil Bearer TokenRequest Token
    Langkah 2: kirim OTPSub Request Pin (Send OTP)
    Langkah 3: verifikasi OTPSubscribe Confirm OTP
    Langkah 4: berhenti langgananUnsubscribe

    Request Token

    DCB V2 GET https://api.airpay.mobi/api/v2/ext/{country}/wap/{service}/YOUR_API_KEY/token/

    Mengambil Bearer Token memakai Basic Auth (username = clientId, password = clientSecret).

    Path

    PathNilai
    country{country}
    channelwap
    service{service}
    apikeyYOUR_API_KEY

    Autentikasi

    Basic Auth: Authorization: Basic Base64(clientId:clientSecret). Lihat Autentikasi.

    Response sukses (200)

    FieldTipeKeterangan
    codeinteger200 bila sukses.
    messagestringsuccess bila sukses.
    data.tokenstringBearer Token untuk langkah berikutnya. Berlaku 1 jam.
    Token kedaluwarsa setiap 1 jam. Setelah kedaluwarsa, panggil Request Token lagi.
    Contoh body hanya ilustrasi bentuk respons; nilai token adalah contoh.

    Delivery Notification

    DN GET [IPADDRESS]:[PORT]/dn/

    Delivery Notification (DN) menunjukkan apakah pesan terkirim dan ditagihkan ke handset pengguna. Percobaan yang gagal mengembalikan negative acknowledgment (FAIL). Messaging Platform meneruskan DN dari operator jaringan ke URL content provider dengan method GET. Pastikan firewall CP mengizinkan akses dari IP Messaging Platform.

    Query parameters

    FieldTipeWajibKeterangan
    operatorstring(50)YaNama operator.
    click_idstring(50)TidakID pelacakan kampanye. Ada pada contoh FP; tidak ada pada contoh RENEWAL.
    eventstring(50)YaJenis notifikasi: FP (pembelian pertama) atau RENEWAL (perpanjangan).
    sdcstring(50)YaShort code tujuan pengguna mengirim permintaan.
    msisdnstring(50)YaNomor telepon pengguna/pengirim (terenkripsi tergantung geo dan layanan).
    servicestring(50)YaNama layanan.
    trx_idstring(150)YaID transaksi milik merchant, yaitu trx_id yang dikirim merchant saat memanggil API.
    trx_datestring(50)YaTanggal transaksi, format YYYY-MM-DDTHH:MM:SS±HH:MM.
    statusstring(50)YaKode status. Lihat Kode status DN.
